# D-Fence — independent execution review of the live deployment

Graded 2026-09-05 against `https://dfence-sc2006.azurewebsites.net` by an independent reviewer
briefed as a TA marking execution quality, then spot-checked against the running system and the
source. Every number below was reproduced, not taken on trust; where my figure and the reviewer's
differ, both are given.

**Overall: B−.** The craft is above the cohort — real Entity/Control/Boundary separation, an
injected transition table that refuses illegal moves in actionable prose, driver contributions that
genuinely sum to the reported score, live ingestion against three government APIs, and a security
posture better than most final-year work. But the course marks a system that demonstrably works on
live data, and the flagship output is wrong in ways a marker sees in ten seconds.

## Corrections to the brief

**There are three roles, not four.** `src/entity/enums.ts:10` defines `Resident`,
`OperationsManager`, `CleaningCrew`. The string "Moderator" appears **zero** times in `src/` and
zero times in `REQUIREMENTS.md`; moderation is an Operations Manager function on
`/api/ops/moderation/*`, and `AdminRoutes.ts` refuses unknown roles with "is not one of the three
roles (2.2.1)". Do not say "four roles" or "Moderator" in the demonstration.

**Rainfall being zero is not primarily a bug.** Singapore has not rained: all 17,685 stored
readings across 88 stations are 0.0 mm, and an independent fetch of the live data.gov.sg endpoint
returned 88 stations all at 0.0. The parser is correct. The real defect is subtler — the 72-hour
accumulation driver reports a *measured* 0 when only 26 hours of history exist, and
`excludedDrivers` is empty and `isDegraded` false on all 43 rows. The system does not distinguish
"no rain" from "no data".

## Root cause of both headline defects

NEA reissues a fresh `OBJECTID` for the same locality on every publish. `ClusterRepository.ts:101`
upserts `ON CONFLICT (object_id)`, so each publish inserts 16 brand-new rows. `deactivateAbsent()`
**exists and is implemented** at `ClusterRepository.ts:143` and is unit-tested at
`tests/analytics.test.ts:172` — and is called from **no production code path**. Verified: a search
for `deactivateAbsent` across `src/` and `tests/` returns only the definition, its in-memory twin,
and that one test.

The same identity failure kills the growth driver: because every row is a new object id, the diff
finds no predecessor, so `change_class = 'NEW'` on all 43 rows and `case_delta = 0`. The data is
already there — Bishan St 12 went 2 to 3 cases between publishes and was recorded as two unrelated
new clusters.

**Operational harm, demonstrated.** A work order was run to Verified and a treatment record
written; the priority table afterwards still showed ranks 1–3 as the same locality with
`daysSinceLastTreatment 0` and `workOrderStatus null` on two of the three. You fog Lentor and two of
three identical rows still say untreated.

## Ranked defects

1. **Cluster duplication — dashboard overstates Singapore's case count ~2.9x (1,375 vs ~465).**
   Small fix: call `deactivateAbsent(seenObjectIds)` at the end of `ClusterIngestionJob.persist`.
   Highest ratio of damage removed to effort in the project.
2. **No cluster can reach Medium; High is mathematically unreachable.** Medium fix: carry cluster
   identity across publishes by locality/geometry so `case_delta` computes. Restores 20% of the
   weight and lifts the ceiling to 80. Do **not** simply lower the thresholds — `SCORING-SPEC.md:156`
   already commits to recalibrating against observed data, and a marker will read it as gaming.
3. **The Resident role cannot be activated on the deployment.** Registration works, sign-in is
   correctly gated, no email is ever sent, and the token goes to a console. The team's own UAT
   prints "1 failed, 10 skipped" against production. Small fix: seed a verified resident the way the
   manager is seeded. (The harness *can* now read the token remotely via the Kudu log stream — see
   `DEPLOY.md` section 6 — but the deployed system still cannot be used by a human resident.)
4. **Photographic evidence is never stored, and the gate is hollow.** `report_photo` has 0 rows;
   `SupabaseStorageGateway` is instantiated nowhere (verified: the only occurrence in `src/` is its
   own class declaration). Completing with no photo keys is correctly refused; completing with
   `photoKeys: ["not-a-real-file-at-all"]` returns **200**. UAT beat 8.3.10 reads PASS for a
   requirement that is not met — the clearest case of a green harness over a hollow feature.
5. **`rescoreCluster` ignores its argument and runs a full ingestion cycle.** Verified:
   `server.ts:459` reads `{ rescoreCluster: async () => cycle('MANUAL') }`. Verifying one work order
   took 30.7 s, identical to a full manual refresh. A frozen button in front of the marker, and it
   can materialise 16 more duplicate rows mid-demonstration.
6. **The audit trail does not exist.** `audit_record` has 0 rows; `server.ts:133` constructs an
   `InMemoryAuditStore` in production; `AuditRecordRepository.save()` throws `not implemented`; and
   there is no audit route at all. `WorkOrderRoutes.ts` documents that work-order history
   deliberately lives in the audit trail and that "the client reads history from the audit
   endpoint" — that endpoint does not exist, so 2.4.1/2.3.8 are unsatisfiable. Not previously on
   the open-items list.
7. **Unmatched `POST /api/*` returns an Express HTML error page.** Verified live: it returns
   `<!DOCTYPE html>...<pre>Cannot POST /api/does/not/exist</pre>` while unmatched GET correctly
   returns `{"error":"no such route","remedy":"check the path"}`. The catch-all is registered for
   `get` only.
8. **Session is in-memory only — refreshing the page signs you out.** `localStorage`,
   `sessionStorage` and `document.cookie` appear 0 times in the bundle.
9. **Seven endpoints have no client screen**: `/api/ops/analytics` (7.3.x — five charts built,
   nobody can see them), `/api/ops/priority.csv` (7.4.2/7.4.3), `/api/reports/:id/corroborate`,
   `/api/account/delete` (PDPA), `/api/auth/verify`, `/api/locations/:id/alerts`,
   `/api/alerts/link/claim`. Client route `/locations/:id` does not exist, confirming the `/alerts`
   dead link (6.1.1/6.1.3).
10. **Zero cross-session propagation.** `setInterval`, `EventSource` and `WebSocket` all appear 0
    times in the 212 KB bundle. One user's action is invisible to another until manual reload.
11. `403` responses drop the `remedy` field every other 4xx carries; anonymous requests get `403`
    rather than `401` with no `WWW-Authenticate`.
12. `priority_score` holds 16,027 rows for 43 clusters in ~26 h (~373 each) — unbounded write
    amplification from rescoring every cycle.
13. `/api/ops/priority` uses `raw`/`normalised`; `/api/map/clusters/:id` uses
    `rawValue`/`normalisedValue`.
14. No Content-Security-Policy; `X-Powered-By: Express` not suppressed.

## What is genuinely strong, and should lead the demonstration

Multi-user interaction is the best axis (7/10) and it is real. Three concurrent bearer sessions were
driven end to end: manager creates crew, raises a work order, assigns it; the crew member sees it on
the next request; the *other* crew member gets a `404` indistinguishable from not-found (correct per
2.3.7); accept, start, complete with evidence, manager verifies, a treatment record is written.

Conflict handling is implemented rather than hand-waved. Observed refusals:

- crew B accepting crew A's order — `422 "only the assigned crew member may make this move"`,
  remedy `"the work order is Assigned"`
- complete before accept — `422 "the state table permits no Assigned to Completed move by a
  CleaningCrew"`
- verify twice — `422 "Verified is terminal"`

Every refusal names the rule *and* the state the caller's client is stale about — which is what
8.3.16 asks for, and better than most professional APIs.

Also strong: weights sum to exactly 1.00 and driver contributions reproduce the reported score to
within 0.1 on all 43 rows; `SCORING-SPEC.md` argues log-scale normalisation with real justification;
ingestion returns `UNCHANGED` on an unmodified feed via a content hash; per-source health with
`lastSuccessAt` and `consecutiveFailures`; HSTS, `nosniff`, `X-Frame-Options: DENY`,
`Referrer-Policy: no-referrer`, HTTP to HTTPS 301, no secrets in the bundle, lockout after four
failed attempts; and sub-second responses under 8-way concurrency on a B1 (0.74–0.99 s).

## Live data update, in detail

It is genuinely live, provable three ways. `POST /api/ops/sources/refresh` returned real per-source
outcomes including `UNCHANGED` with `featureCount: 0` — a content-hash short-circuit doing real
work. The `ingestion_run` table holds 541 Rainfall runs, 523 Clusters `UNCHANGED`, 3 Clusters
`SUCCESS` and 58 Forecast runs over 26 hours, an automatic cycle roughly every 2.9 minutes.
`rainfall_reading` holds 17,685 rows spanning 2026-09-04T01:50Z to 2026-09-05T04:00Z across 88
stations.

Two honesty gaps: source health calls Rainfall healthy and not stale on a run that persisted
`featureCount: 0` — a source returning nothing shows green; and degradation behaviour under a real
source outage was **not observed**, because nothing was failing. The code paths exist but were seen
only in their negative state.

`src/scheduler.ts` still carries `// TODO(F1): register the cron schedules` and is dead code; the
real scheduling is a `setInterval` at `server.ts:377`.
